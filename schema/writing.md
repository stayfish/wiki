# 问题驱动的中文技术写作 Workflow

本规范同时用于对话回答和公开 Wiki。它吸收清晰技术博客中常见的高层特征：从真实问题出发，沿推理自然引出术语、公式和实验；参考包括科学空间一类问题驱动的中文技术文章，但不模仿任何作者的个人口癖或标志性表达。

目标不是把论文逐段翻译成中文，而是让读者沿一条可检查的推理链真正理解：问题怎样出现，直接做法为什么不够，论文改了什么，这个改动会产生什么行为，证据支持到哪里。

## 1. 先找一个具体问题

每个回答或内容块先写读者能够想象的失败情形，再引入抽象名词。例如讨论 full-duplex 时，先问“助手说话期间用户改口，它能不能停下来并使用新信息”，再定义 streaming、real-time 和 full-duplex。不要用模块名、论文口号或分类表开场。

进入下一段前检查：读者是否已经知道现在要解释什么，以及不解决它会发生什么。若答案是否定的，先补具体场景，不要继续增加术语。

## 2. 术语以清楚为准，不以翻译率为准

- 中文已有自然、稳定且不损失含义的说法时使用中文。
- 原词更准确或中文译法生硬时，直接保留 `chunk`、`window`、`token`、`Attention`、`KV cache`、`boundary token` 等英文。首次出现时用一句中文说明它在当前语境中做什么，之后保持同一写法。
- 优先沿用原文术语。不要为了显得中文化而另造近义名词，也不要在 `chunk`、`window`、`time slot` 之间无理由切换。
- 抽象指标先写成可观察的现象，再给名称和符号。例如先写“已经生成但还没播出的音频有多长”，再定义 `backlog` $B(t)$；先写“环境改变后，旧内容还会继续播放多久”，再给指标名。
- 一个术语如果不能帮助后文推理、公式或查证，就删掉。

## 3. 用问题链组织段落

一个完整技术段落通常沿下面的顺序展开，但不必机械地把六步写成小标题：

1. **问题**：具体哪里会失败？
2. **直接做法**：最自然的方案是什么？
3. **缺口**：它为什么在当前条件下不够？
4. **设计**：论文加入了什么表示、接口或训练信号？
5. **行为**：这个设计在训练和推理时具体怎样运行？
6. **证据边界**：哪个实验支持它，仍有什么没有测？

相邻段落要有因果承接。常用的自然连接是“问题出在……”“于是……”“具体来说……”“这带来一个代价……”“但这张表只能说明……”。避免把论文原句依次翻译后堆在一起，也避免使用大量名词短语代替动作。

## 4. 先写动作，再写名称

优先使用有主体的句子：谁读入什么、何时做决定、产生什么输出、状态怎样传到下一步。首次介绍模块时，先说明动作，再给名字。

例如，与其写“TAIL 实现累计对齐”，不如写：“训练数据先按发音时间戳把 text token 分到各个 `chunk`；推理时，模型逐 token 生成，首次生成 `boundary token` 就结束当前 `chunk`。这套做法叫 TAIL。”

少用没有可观察含义的名词，如“承诺量”“语义陈旧度”“对齐误差”。确实需要抽象名词时，紧跟可测定义。

## 5. 公式从推理中长出来

公式出现前先说明它要回答什么问题。变量在公式附近定义，公式后把它还原成一次具体操作或判断。不要先陈列公式再补一段翻译。

推导只保留影响机制理解的步骤。若论文没有理论推导，就分析目标函数、信息流或复杂度，不用额外数学包装简单流程。

## 6. 实验是论证，不是成绩单

每张表围绕一个问题阅读：作者想排除哪种解释，结果改变了什么判断，还有哪个替代解释没有排除。只保留影响判断的数字。

先给一句结论，再展示必要数据，然后明确边界。例如：“Table 10 说明 TAIL 仍能生成可懂语音，也显示英文 WER 变差；它没有测量 queue backlog，因此不能证明长期同步更好。”

## 7. 证据身份写进语气

正文必须让读者分辨四种信息，但不需要每句话都贴标签：

- “论文定义/报告/明确写道”表示作者陈述；
- “Table 3 中……，因此在该设置下……”表示实验支持；
- “一种更谨慎的理解是……”表示分析推断；
- “原文没有给出……，因此目前无法判断”表示未知。

用户在讨论中形成的判断要明确归给用户或本次阅读，不能改写成作者观点。结构化 claim 和 evidence sidecar 负责机器可查证性，正文负责自然可读性，两者不能互相替代。

## 8. 两遍修订

第一遍检查忠实度：任务定义、输入输出、模块顺序、训练和推理差异、数字、来源及未知项是否正确。

第二遍只检查阅读感：

- 开头是否给出具体问题，而非论文摘要式判断；
- 每段是否有明确主体和动作；
- 术语是否来自原文并保持一致；
- 是否存在可以改成具体行为的生硬译词；
- 公式前后是否都能用自然语言复述；
- 表格是否回答了一个问题；
- 删除小标题后，段落之间是否仍能顺着读下去；
- 是否把“论文没测”明确写出来，而没有用流畅叙事补齐缺口。

如果一句话准确却不自然，优先拆成两句：第一句写发生了什么，第二句写这意味着什么。
