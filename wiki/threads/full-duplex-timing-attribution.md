# 如何验证全双工模型真的保持了时间同步

## 为什么重要

[[minicpm-o-4-5]] 用共享时间窗和 TAIL 把“每窗应承诺多少文字”转成自回归边界预测。该表示足以产生时间对齐的训练序列，却不保证真实扬声器、网络和设备调度发生抖动后仍能维持同步。若只报告 RTF、CER/WER 或定性 demo，模型内部时间轴、实际播放进度和环境墙钟仍可能逐渐分叉。

## 当前理解

实时全双工至少包含三个时钟：模型 token 时钟、语音播放时钟与外部环境墙钟。MiniCPM-o 4.5 的公开方法用离线发音时间戳对齐前两者的训练样本，推理时依靠边界 token、历史序列和 KV cache 隐式调度；公开材料没有显示模型读取真实 playhead 或队列长度。

因此，TAIL 当前最稳妥的定位是“学习到的开环时间先验”。它是否能在真实执行偏差出现后闭环恢复仍未知。这个问题也适用于固定或动态窗口的其他 duplex 系统：改变模型协议不等于观察到了执行状态。

## 支持证据

- [[minicpm-o-4-5]] Section 3.4 明确用文本 token 的发音起止时间构造变长时间窗监督，并让此前延迟影响后续窗的目标文本量。
- 官方推理实现显示动态长度来自自回归 boundary，常规窗有近固定语音 token 预算与最大文字 token guardrail，但未见公开的播放器误差变量。
- 论文 Table 12 的 RTF 证明优化运行时可跟上现实时间；Table 10 只测可懂度与说话人相似度，没有测播放积压、语义陈旧度和恢复时间。
- 后续 AdaptDuplex 开始直接报告 interruption、delay、overlap 与 turn-taking 指标，说明交互时序可以脱离通用能力分数独立评估。

## 反例或冲突

- 模型内部每窗生成量可以完全符合训练分布，而播放器因网络或设备抖动持续积压；如果模型看不到真实队列，它没有可靠信号区别这两种状态。
- RTF 小于 1 只能说明平均计算吞吐足够，不能排除文本一次承诺过多、旧波形未取消或短时延迟累积。
- boundary 训练使用 teacher forcing；推理时过早或过晚的边界会改变后续历史，论文没有报告误差是否会自行恢复。
- AdaptDuplex 的系统结果同时改变模型规模、数据、窗口策略和训练流程，不能把其时序提升单独归因于动态窗口。

## 缺少什么

需要在同一模型、speech decoder、运行时和数据上比较动态边界与匹配平均长度的固定边界，并记录：

| 指标 | 回答的问题 |
| --- | --- |
| 已承诺但未播放的语音时长 $B(t)$ | 是否长期积压 |
| 环境改变到旧内容播放结束的间隔 | 内容是否语义过期 |
| 用户插话到旧波形停止的延迟 | 取消链是否有效 |
| 注入 300/600 ms 抖动后的恢复窗口数 | 策略是否能闭环纠偏 |
| boundary 位置误差与 guardrail 触发率 | 动态长度是否来自正常预测 |
| CER/WER、SIM 与 RTF | 同步收益付出了多少质量和算力代价 |

还需要分别测试回声、重叠说话、长词、数字、停顿、代码切换与十分钟以上连续交互，避免平均短对话掩盖漂移。

## 下一步

1. 在官方 MiniCPM-o 4.5 推理链中加入全阶段时间戳和真实播放器 acknowledgement；
2. 实现 TAIL 与 Fixed-N 两个只改变边界策略的设置；
3. 注入计算、网络和播放抖动，使模型内部历史与真实 playhead 主动分叉；
4. 再加入量化 queue-state token，比较开环 TAIL 与 Playback-Aware TAIL 的恢复速度；
5. 用人类盲评检查更低 backlog 是否以突兀停顿、漏词或语义破碎为代价。

## 何时算回答

当公开或可复现实验能在同一模型内同时报告质量、吞吐、积压、陈旧度、打断残留和抖动恢复，并通过真实 queue-state 干预区分“仅依赖生成历史”与“读取执行反馈”时，可以将本线索闭合为全双工时序控制主题页。
